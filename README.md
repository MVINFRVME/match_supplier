# Match Supplier

Сервис поиска и сравнения поставщиков продуктов питания (ингредиенты, готовая продукция, упаковка, HoReCa и смежное).

Закупщику нужно не «найти ещё десять ссылок», а быстро понять: кто подходит под категорию и город, у кого есть документы и приемлемый порог заказа, кому писать первым. Match Supplier закрывает этот шаг на демо-каталоге (~53 поставщика) и готов к замене источника данных.

---

## Как работает

```
текст запроса или фильтры вручную
              │
              ▼
     разбор текста → те же фильтры, что в форме
              │
              ▼
  фильтры отсекают выдачу → оценка 0–100 → сортировка
              │
              ▼
 карточка → сравнение (до 3) → шортлист → письмо поставщику
```

1. **Запрос.** Можно ввести обычный текст («молоко Екатеринбург самовывоз до 30000») или выставить фильтры руками: категория, города, регионы, сумма, тип доставки, срок, документы.
2. **Разбор текста.** Свободная фраза превращается в те же поля фильтров, что уже есть в интерфейсе (категория, город, регион, лимит суммы, тип доставки и т.д.). Сначала пробуется модель Groq (если задан `GROQ_API_KEY`): она возвращает JSON с этими полями, значения проверяются по справочникам каталога — выдумать несуществующий город или категорию нельзя. Если ключа нет или модель не справилась — срабатывают правила по ключевым словам. В обоих случаях на выходе те же фильтры, что можно выставить руками.
3. **Выдача.** Поставщики, не прошедшие фильтры, не показываются. Остальных ранжирует **оценка соответствия** с разбором по пунктам (клик по оценке).
4. **Сравнение.** До трёх поставщиков; блок «с кем лучше связаться» учитывает последний запрос (категория, география, тип доставки).
5. **Шортлист.** Воронка статусов и заметки — пока в браузере (localStorage).
6. **Outreach.** В карточке — готовый текст первого письма (`mailto`); известные условия из профиля не переспрашиваются.

## Оценка соответствия (0–100)

Базовые веса нормируются на 100:

`макс по пункту = 100 × вес / сумма весов участвующих пунктов`.

### Что входит

| Что смотрим | Базовый вес | Когда участвует | Как считается |
|---|---|---|---|
| Категория | 40 | Если выбрана в фильтрах | Совпало — полный вклад, нет — **0** |
| Город / регион | 40 | Если выбран в фильтрах | Совпало — полный вклад, нет — **0** |
| Тип доставки | 40 | Если выбран в фильтрах | Совпало — полный вклад, нет — **0** |
| Срок доставки | 20 | Всегда | Чем быстрее, тем выше; чистый самовывоз — полный балл; вне заданного диапазона — почти 0 |
| Минимальная сумма заказа | 20 | Всегда | Чем ниже, тем выше; выше вашего лимита — **0** |
| Документы | 20 | Всегда | Указаны / не указаны (число сертификатов не важно) |

**Цена в оценку не входит** — в карточке остаётся текстовый ориентир (`price_hint`).

Город, регион и тип доставки ещё и **жёстко отсекают** выдачу. В сравнении рекомендация предпочитает тех, кто совпал с гео и типом доставки запроса (если они заданы).

### Сколько баллов после пересчёта

Зависит от того, сколько из трёх фильтров (категория / гео / тип доставки) выставлены:

| Выставлено фильтров | Примерно максимум по пунктам |
|---|---|
| Все три | по ~22 на каждый фильтр и по ~11 на срок, сумму и документы |
| Два | по ~29 на каждый фильтр и по ~14 на срок, сумму и документы |
| Один | 40 на фильтр и по 20 на срок, сумму и документы |
| Ни одного | по ~33 на срок, сумму и документы |

Невыставленный фильтр в оценку не попадает — его доля уходит в остальные. Код: [`backend/app/score.py`](backend/app/score.py).

## Что сделано по требованиям ТЗ

| Требование | Реализация |
|---|---|
| Поиск по категории | Фильтр + текстовый поиск («молоко» → «Молочные продукты») |
| Город или регион | Мультивыбор города и региона работы; фильтр + вклад в оценку |
| Основная информация | Профиль: описание, категории, гео, условия, документы, тип доставки |
| Контакты, сайт, источник | Телефон, email, сайт, источник, дата обновления |
| Помочь решить, с кем связаться | Оценка с разбором, сравнение до 3, рекомендация с текстом «почему» |
| Минимальный объём / сумма заказа | Поле + фильтр «не выше лимита» + вклад в оценку |
| Примерная цена | `price_hint` в карточке и сравнении; в score не входит |
| Документы / сертификаты | Список, фильтр «только с документами», в оценке бинарно есть/нет |
| Условия доставки | Текст условий + `delivery_types` + срок в днях |
| Регион работы | Города и регионы покрытия |
| Комментарии / заметки | Заметки в шортлисте |

## Что добавлено сверх ТЗ

1. **Запрос свободным текстом** → те же фильтры, что в форме (правила + опционально Groq).
2. **Тип доставки** как фильтр и критерий оценки: самовывоз / транспортом поставщика / до ТК.
3. **Сравнение с контекстом поиска** — рекомендация опирается на последний запрос.
4. **Шортлист-воронка** — статусы «в работе → связались → ждём прайс → не подошёл».
5. **Готовый текст запроса** поставщику с учётом того, что уже известно о нём.
6. **Оценка качества данных** профиля — полнота, свежесть, верификация.
7. **Объяснимость** — разбор баллов по клику; таблицы весов в справке и здесь.
8. **Сохранение поискового контекста** — возврат на «Поиск» не сбрасывает фильтры.

## Стек и почему так

- **Backend: FastAPI + Pydantic, зависимости через [uv](https://docs.astral.sh/uv/).** Тонкий API; OpenAPI из коробки; логика поиска и оценки — обычный Python.
- **Frontend: React + Vite + TypeScript + Tailwind.** Фильтры, сравнение и шортлист без перезагрузки страницы.
- **Данные: демо-каталог** в [`backend/data/suppliers.json`](backend/data/suppliers.json). Публичного удобного API агрегаторов нет; для прототипа важнее сценарий закупщика. Модель и API рассчитаны на замену фида.
- **Деплой: Docker.** Образ собирает фронт и API; снаружи — Nginx на порт контейнера.

## API

Документация: `http://<host>/docs`

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/health` | Проверка живости |
| GET | `/api/meta` | Категории, города, регионы, макс. срок по каталогу |
| POST | `/api/parse-query` | Разбор свободного текста в фильтры |
| GET | `/api/suppliers` | Поиск и ранжирование |
| GET | `/api/suppliers/{id}` | Карточка со score и качеством данных |
| GET | `/api/compare` | Сравнение до 3 id + рекомендация |
| POST | `/api/suppliers/{id}/outreach` | Текст запроса поставщику |

Основные query-параметры: `q`, `category`, `city`, `region`, `max_moq`, `min_lead_days`, `max_lead_days`, `delivery_type`, `require_certificates`.

## Локальный запуск

### Backend

```bash
cd backend
uv sync
uv run uvicorn app.main:app --reload --port 8000
```

### Frontend

```bash
cd frontend
npm install
npm run dev
```

Открыть `http://127.0.0.1:5173` — Vite проксирует `/api` на backend.

### Groq (необязательно)

Без ключа разбор текста работает на правилах. Шаблон — [`.env.example`](.env.example), файл `backend/.env`:

```
GROQ_API_KEY=gsk_ваш_ключ
GROQ_MODEL=openai/gpt-oss-20b
```

Если ключа нет или запрос к модели упал — откат на правила, сервис продолжает работать.

## Деплой

```bash
cp .env.example .env   # при необходимости GROQ_API_KEY
docker compose up -d --build
```

Контейнер слушает `127.0.0.1:8000` на сервере (не в интернет напрямую). Снаружи сайт открывается через Nginx на 80/443 — пример: [`deploy/nginx.conf.example`](deploy/nginx.conf.example).

## Что дальше

- **База вместо JSON и localStorage** — каталог и шортлисты закупщиков в БД (PostgreSQL или аналог), чтобы данные не жили только в браузере.
- **Аутентификация и роли** — закупщик / админ; без этого общий шортлист и модерация каталога не заведутся.
- **Админка** — правка карточек, модерация заявок, источник и дата обновления по полям.
- **Кабинет поставщика** (опционально) — самостоятельная регистрация и обновление профиля вместо только ручного/парсерного наполнения каталога.
- **Партнёрский или свой фид** вместо демо-`suppliers.json`.
- **История условий и RFQ** сразу нескольким поставщикам.

Для текущего прототипа и защиты отдельный слой автотестов не обязателен: сценарий проверяется руками по основному флоу.
